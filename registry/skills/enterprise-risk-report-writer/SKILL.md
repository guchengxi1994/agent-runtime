# 企业涉法涉诉案件分析报告写作器

把这个 skill 视为“最终成稿层”，而不是数据查询层。

当前默认口径是**检察机关/检察院视角的正式成稿**，不是第三方咨询公司口径，也不是一般业务部门简报口径。

只有在以下条件基本满足时才使用：

- 已有可用的量化结果
- 已有可用的案例或样本证据
- 已经判断哪些图表值得放进报告

如果这些条件还不满足，应先回到数据查询、案例检索或证据补充阶段。

## 触发后的工作方式

1. 先整理证据包，再下笔：
   - 已确认的核心结论
   - 支撑每个结论的数字
   - 可引用的代表性案例或样本
   - 如上游已调用 `qwen-web-analysis(mode=explain)`，吸收其中可用的“机制解释、外部对照、治理含义”
   - 如上游已调用 `qwen-web-analysis(mode=recommend)`，吸收其中可用的“外部可借鉴经验、对策建议”
   - 如果没有调用、调用失败或价值不高，直接按本地证据成稿
   - 当前不能确认或不宜扩写的部分
   - 如果上游没有指定单一企业，则默认把证据包组织成“天宁区全区企业涉法涉诉案件分析报告”，而不是企业专项稿
2. 只围绕证据最强的 2-4 个发现组织全文。
3. 把前面 skill 返回的结构化结果转成业务语言和正式报告语言。
4. 最终输出只给成稿，不要把分析过程、工具过程和技术实现混进正文。

## 强约束

1. 最终必须输出**中文正式报告**。
2. 不允许把以下内容写进正文：
   - SQL
   - JSON
   - 图表 option
   - 数据库表名
   - 字段名
   - skill 名称
   - tool 名称
   - “我查询了什么”“我调用了什么”之类过程描述
3. 不要中英文混杂行文。
4. 不要把报告写成提纲、开发说明、数据工程 TODO 或问答纪要。
5. 如果某部分证据不足，就缩写、跳过或弱化对应判断，不要硬凑，也不要单列“数据局限说明”“待确认事项”或后续规划。
6. 只写当前实际纳入的数据所支持的内容。数据来源与范围部分应正向描述“本次报告纳入了哪些数据”，不要扩写无证据内容，也不要反向罗列未接入、未使用或假设性数据源。
7. 图表只在正文中写“图1/图2/图3”及解读，不粘贴原始规格。
8. 不要单独输出“图表清单”来罗列图名；每张图应放在对应分析段落附近，并使用单独成行的 `图1：……`、`图2：……` 作为前端内联锚点。
9. 图题、图例、系列名称、分类标签默认使用中文，不要把字段名、英文指标名或枚举代码直接写给读者。
10. 如果用户请求的是“完整报告”而非“企业专项报告”，不要在开头追问目标企业或特定关注维度，直接按全区总报告成稿。
11. 如果正文包含“治理意见建议”，默认应体现检察机关服务党委政府决策、立足法律监督参与社会治理的写法，而不是纯企业管理建议。

## 默认成稿顺序

除非证据明确要求调整，否则优先采用以下顺序：

1. 标题
2. 引言或执行摘要
3. 数据来源、分析范围与说明
4. 总体态势
5. 重点结构或趋势分析
6. 代表性案例或样本摘要
7. 风险成因深层分析
8. 治理意见建议
9. 结语

## 写作要求

- 标题体系尽量采用正式中文体例：
  - `一、`
  - `（一）`
  - `1.`
- 以完整段落为主，表格和 bullet 只能辅助，不得替代主体叙述。
- 每个核心章节尽量遵循：
  - 先给判断
  - 再给证据
  - 再解释为什么重要
- 同一份报告中，避免同时出现“正式公文语体”和“开发调试语体”。
- 表达要像送审稿、汇报稿或客户成稿，而不是分析控制台。
- 若以检察院口径成稿，正文应自然体现“法律监督、检察履职、府检联动、服务党委政府治理决策”等表述框架。

## 分析深化要求

不要把“分析”写成轻量版的数据播报。正式成稿至少要做到以下几点：

1. 总体态势：
   - 不只写总量和占比，还要说明结构主导面是什么、意味着什么。
2. 趋势分析：
   - 不只写“总体平稳/有所波动”，还要识别阶段变化、峰值/低值月份、可能的业务或法治含义。
3. 行业与属地分析：
   - 不只罗列前五或前十，还要写头部集中度、梯度差异、重点板块压力，以及为什么这些板块更容易积聚案件。
4. 主体结构分析：
   - 对中小微企业、民营企业、重点高频涉诉主体等，要写清楚这反映的是何种治理短板或经营法治薄弱点。
5. 案例部分：
   - 案例必须服务于前文观点，提炼“纠纷机制/风险传导链条/治理启示”，不要简单复述案情。
6. 风险成因深层分析：
   - 若已有 `qwen-web-analysis(mode=explain)` 结果，应优先吸收其中与本地高发行业、重点街道、主要案件类型直接对应的机制解释。
   - 不要只写宏观经济套话；至少要把本地证据与成因机制逐一挂钩。
7. 治理意见建议：
   - 若已有 `qwen-web-analysis(mode=recommend)` 结果，应优先吸收其中与本地最高频问题相对应的可借鉴经验和建议动作。
   - 建议段不追求大而全，优先写 3-5 条与本地问题直接对应、表述克制的建议。
   - 如按检察院口径成稿，优先采用“导语 + 分条建议”的体例，每条建议尽量拆成：
     - `党委政府主责`
     - `检察履职协同`
   - 可以自然使用“府检联动”“法律监督”“社会治理检察建议”“支持起诉”“行政检察”“行政公益诉讼”“行刑反向衔接”“涉案企业合规”等检察履职语言，但前提是与前文问题直接对应。
8. 结论表达：
   - 结尾应回扣前文主发现，避免出现与证据脱节的泛化表述。

联网分析只是补强项，不是必需项。没有它，报告也应能独立成立。

如果证据足够，优先在以下位置补强“解释层”：

- 为什么某类行业更集中
- 为什么某个板块案件压力更高
- 为什么某类主体更容易成为高频涉诉对象
- 当前结构对治理资源配置意味着什么

如果证据足够，优先在以下位置补强“建议层”：

- 针对高频涉诉行业有哪些外部成熟做法
- 针对案件压力最高街道可借鉴哪些前端化解机制
- 针对高发事项类型，下一步有哪些更有针对性的治理动作

## 使用图表时的要求

- 先决定图是否真的增强理解。
- 正文里只解释图表支撑的判断。
- 图卡之外不要重复堆砌同一批原始数字。
- 如果图表和正文冲突，以正文的证据解释为准，并明确数据局限。

## 证据边界表达要求

如果某一判断的证据不够强，应直接缩短、跳过，或在相关段落里轻量处理，不要额外拉出“数据局限说明”“待确认事项”或“后续规划”章节。

如果现有数据已经足够支撑正文，就不要主动补一句“暂未覆盖某某数据源”。除非用户明确要求做数据范围盘点，否则正文不写未纳入清单。

不要默认写成：

- 建议补字段
- 建议扩表
- 建议补 schema
- 建议查看完整列名
- 后续还需纳入某某数据源

除非用户明确要的是技术方案而不是正式报告。
