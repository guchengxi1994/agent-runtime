# 风格参考

这不是死模板，而是“接近正式客户成稿”的风格轮廓。

## 应呈现出来的感觉

- 像正式报告，不像问答回复
- 像送审稿，不像调试说明
- 像业务分析成稿，不像数据库分析笔记

## 推荐风格特征

1. 标题完整、正式，必要时可带副标题。
2. 开头先说明研究对象、时间范围、报告目的。
3. 主体章节围绕几个真正重要的案件特征发现展开，不平均铺开。
4. 表格只用于承载关键数字、重点分类或代表性样本。
5. 建议部分要和前文发现一一对应，不能泛泛空喊。
6. 结尾应有收束感，像一份报告的结束，而不是一次对话的停止。

## 建议模仿的骨架

适合大多数正式案件分析报告的骨架：

1. 标题
2. 引言
3. 数据来源与分析说明
4. 总体情况
5. 重点发现
6. 代表性样本或案例
7. 研判结论
8. 建议
9. 结语

## 不该出现的内容

- “下面是 SQL”
- “图表 JSON 如下”
- “我调用了 pg-report-query”
- “当前表结构如下”
- “关键字段包括……”
- “rows / columns / schema”
- 一大串工具名、skill 名称或执行过程

## 当证据不足时

不要硬写成长篇。

正确做法：

- 缩短该节
- 明确说明局限
- 保留谨慎判断

错误做法：

- 用技术说明填充篇幅
- 用字段问题替代业务判断
- 用英文标签和调试术语拼接正文
