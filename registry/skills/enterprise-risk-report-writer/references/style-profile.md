# 风格参考

这不是死模板，而是“接近正式客户成稿”的风格轮廓。

## 应呈现出来的感觉

- 像正式报告，不像问答回复
- 像送审稿，不像调试说明
- 像业务分析成稿，不像数据库分析笔记
- 如果任务背景是检察院课题、检察履职分析或府检联动专题，还应像检察机关报送党委政府的决策参阅材料

## 推荐风格特征

1. 标题完整、正式，必要时可带副标题。
2. 开头先说明研究对象、时间范围、报告目的。
3. 主体章节围绕几个真正重要的案件特征发现展开，不平均铺开。
4. 表格只用于承载关键数字、重点分类或代表性样本。
5. 结尾应有收束感，像一份报告的结束，而不是一次对话的停止。
6. 如果正文包含“风险成因深层分析”或“治理意见建议”，这两部分都应与前文本地证据直接呼应，而不是独立悬空。
7. 如果正文包含“治理意见建议”，且口径为检察院视角，建议自然使用以下表述框架：
   - 党委政府主责
   - 检察履职协同
   - 法律监督
   - 府检联动
   - 社会治理检察建议
   - 支持起诉
   - 行政检察 / 行政公益诉讼
   - 行刑反向衔接
   - 涉案企业合规

## 分析表达的最低标准

以下写法偏弱：

- “排名前五的分别是……”
- “整体较为平稳，值得关注”
- “某板块案件较多，值得关注”

更好的写法应补上：

- 这说明了什么结构特征
- 为什么会出现这种集中或波动
- 它对区域案件结构、法治环境或企业经营风险意味着什么

如果写到“治理意见建议”，还应补上：

- 其他地区或公开治理实践里有哪些可借鉴做法
- 这些做法为什么适合当前本地高发问题
- 建议动作与前文哪个发现直接对应
- 如为检察院口径，建议还应说明检察机关如何依法协同发力，而不是只写行政部门动作

也就是说，正文要尽量形成：

判断 -> 数字 -> 解释 -> 含义

而不是：

数字 -> 数字 -> 数字 -> 泛泛建议

## 建议模仿的骨架

适合大多数正式案件分析报告的骨架：

1. 标题
2. 引言
3. 数据来源与分析说明
4. 总体情况
5. 重点发现
6. 代表性样本或案例
7. 研判结论
8. 建议
9. 结语

## 不该出现的内容

- “下面是 SQL”
- “图表 JSON 如下”
- “我调用了 pg-report-query”
- “当前表结构如下”
- “关键字段包括……”
- “rows / columns / schema”
- 一大串工具名、skill 名称或执行过程

## 当证据不足时

不要硬写成长篇。

正确做法：

- 缩短该节
- 直接弱化该判断
- 保留谨慎判断

错误做法：

- 用技术说明填充篇幅
- 用字段问题替代业务判断
- 用英文标签和调试术语拼接正文
- 顺势补一段后续规划或未纳入数据源清单
