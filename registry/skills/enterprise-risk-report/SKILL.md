# 企业涉法涉诉案件分析报告编排框架

把这个 skill 视为报告生产用的 harness，而不是普通问答助手。

## 强制输出约束

以下约束优先级高于一般写作自由度，正式报告必须遵守：

1. 最终正文必须是**中文正式报告**，不允许中英文混杂行文。
   - 允许保留的英文仅限于企业英文名称、法规/系统固有缩写、案件编号、字段原值中无法翻译的部分。
   - 不要出现 `overall`、`top 10`、`trend`、`summary`、`json`、`sql`、`schema`、`rows`、`columns` 这类英文叙述词。
2. 不要把工具过程、SQL、JSON、图表规格、数据库表名、字段名、skill 名称、tool 名称写进报告正文。
   - `PostgreSQL`、`enterprise_risk_events`、`case_title`、`chart-spec-builder` 这类词默认属于技术实现细节。
   - 如果用户没有明确要求技术附录，就不要在正文解释表结构、字段覆盖、完整列名或查询过程。
3. 图表在正文中只写成“图1 / 图2 / 图3”及其解读，不要粘贴原始图表 JSON。
   - 图表锚点必须直接放在对应分析段落附近，不要单独整理一个“图表清单”章节来罗列图名。
   - 如需触发前端内联渲染，优先使用单独成行的 `图1：……`、`图2：……`。
   - 只有在正文里确实无法稳定挂图时，才额外使用 `[[chart:图1：……]]` 或 `[[chart:标题]]` 这类显式锚点。
   - 不要在同一位置同时混用 `图1：……` 和 `[[chart:1]]` 这种同编号双锚点写法，以免前端重复插图。
4. 正文应以段落论证为主，不要把整篇报告写成表格堆砌、bullet 堆砌或技术备忘录。
5. 如数据不足，应写成“数据局限”或“待补充事项”，不要转成“建议扩展表结构”“建议补充字段”这类技术实施说明，除非用户明确要求数据治理方案。
6. 如果当前只有司法案件和行政处罚数据，就按这两类数据诚实成稿，不要为了凑齐旧模板而扩写无证据的 12345、综治中心、检察履职内容。
7. 报告标题、一级标题、二级标题尽量采用中文正式体例，例如：
   - `一、`
   - `（一）`
   - `1.`
8. 最终读感要更接近“给领导或客户看的正式成稿”，而不是“给开发者看的分析过程”。

## 核心原则

保持客户习惯的报告风格，但不要把每一份报告都强行塞进同一个僵硬目录。

真正要保持的是：

- 稳定的专业语气
- 可辨识的报告纪律性
- 证据优先的论证顺序
- 根据真实数据形态动态调整的章节结构，而不是死板模板

## 必要路由

1. 先激活并阅读 `references/report-structure.md`。
2. 如果任务依赖本地结构化司法案件、行政处罚等 Excel 数据，而 PostgreSQL 未确认已有数据，先调用 `pg-risk-dataset-sync`。默认不要追问数据路径；应先按它的默认规则使用环境变量目录或 skill 自带 `assets/input/`，只有用户明确要求切换数据集，或默认目录也没有可读文件时才追问。它负责建表、判重和幂等导入，不应删库重建。
3. 在正式写 SQL 或执行 `pg-report-query` 之前，先调用 `pg-table-profile`，确认真实列名、字段类型和低基数字段取值；不要凭空猜列名。
4. 如果需要量化指标、总量、趋势或交叉分析，调用 `pg-report-query`。
5. 如果需要从结构化案件中抽取代表性案例，优先调用 `pg-case-search`。
6. 只有在需要补充本地精选案例，或数据库案例检索链路暂不可用时，才激活 `case-library-review`，先读紧凑索引，再按需读取具体案例文件。
7. 当证据包已经基本齐备、接下来主要任务是“把证据写成正式中文报告”时，必须激活 `enterprise-risk-report-writer`，把最终成稿交给它处理。
8. 如果前端需要图表，调用 `chart-spec-builder`，并把图表规格和文字分析一起返回。
9. 当报告较长时，至少在以下阶段创建 checkpoint：
   - 范围确认后
   - 证据包确认后
   - 叙事方向和提纲锁定后

## 写作流程

1. 先锁定报告范围：
   - report_purpose
   - covered_date_range
   - covered_region_or_organization
   - available_data_sources
   - 如果当前使用的是这批天宁区企业涉法涉诉案件数据，要把 `天宁区` 视为数据全集范围，而不是再作为 `region` 过滤条件；区内地区分析默认指街道、板块、园区等更细粒度属地
   - 如果用户没有明确点名某一家企业，而是要求“完整报告”“全区报告”“天宁区报告”“年度案件分析报告”“涉法涉诉案件分析报告”之类内容，默认将任务理解为**天宁区全区企业涉法涉诉案件分析报告**，不要追问目标企业
   - 在上述全区报告默认模式下，除非用户另有要求，不要再追问“核心关注维度”；应默认覆盖总体态势、月度趋势、行业分布、区内属地分布、案件事项类型、代表性案例/样本、主要问题研判和治理建议
   - 只有当用户明确要求“单家企业专项报告”“某企业深度画像”“某企业异常诊断”时，才进入企业级专项报告模式
2. 检查数据是否已经可用：
   - 如果 PG 中缺少 `enterprise_risk_events` 或行数为 0，先调用 `pg-risk-dataset-sync`
   - 在上述默认导数场景下，不要因为缺少 `data_dir` 就先调用 `request_user_input`
   - 如果查询 skill 返回 `missing_dataset`，立即回退到同步步骤再重试
3. 先理解数据表本身：
   - 调用 `pg-table-profile`
   - 读取真实列名
   - 读取低基数字段的枚举值或高频取值
   - 只在此基础上手写 SQL 或组织 `pg-report-query` 参数
   - 如果查询报 `schema_mismatch`，停止猜测，回到探查步骤
4. 组织证据包：
   - 来自数据库或查询方案的量化指标
   - 来自数据库案例检索或本地精选案例的定性证据
   - 只有确有必要时才引入外部政策或公开来源背景
   - 在进入最终写作前，把证据包压缩成“核心发现 + 关键数字 + 代表性案例/样本 + 局限事项”
5. 下笔前先识别证据形态：
   - 最强信号到底是趋势变化、结构失衡、地区差异、案例模式、治理弱点，还是数据缺口？
   - 当前数据是否足够支撑强结论，还是应该采用更谨慎的诊断语气？
   - 哪 2-4 个发现是真正的主发现，哪些只是辅助观察？
6. 正式写作前先选定叙事主线：
   - 如果时间序列变化最强，用趋势驱动型
   - 如果构成或分层差异最强，用结构驱动型
   - 如果任务是解释异常或问题成因，用问题诊断型
   - 如果任务要落到治理动作或管理建议，用治理与行动型
7. 围绕选定的叙事主线搭建动态提纲：
   - 保持客户熟悉的报告风格
   - 只保留真正有证据支撑的核心模块
   - 数据需要时可以合并或拆分章节
   - 如果某个标准章节证据很弱，就缩短，不要硬凑字数
8. 报告中的每张图都必须满足：
   - 说明为什么需要这张图
   - 生成前端可直接消费的图表规格，但该规格不应直接出现在最终正文
   - 明确这张图支撑的结论是什么
   - 如果调用 `chart-spec-builder`，默认应显式传入真实的 `x_field` 与 `y_fields`；不要只传 `rows` 后期待前端自行猜测
   - 图题、图例、系列名称、分类标签默认使用中文；不要把 `case_count`、`judicial_case`、`administrative_penalty` 这类英文/代码值直接暴露给读者
9. 在最终回答用户前：
   - 若仍处于取证阶段，不要急着成稿
   - 若已进入成稿阶段，应切换到 `enterprise-risk-report-writer` 的写作约束
10. 最终输出应包含：
   - 报告标题
   - 带完整段落的结构化 markdown 正文
   - 图表建议或图表规格
   - 明确的数据限制说明

## 质量要求

- 不要把报告写成只有 bullet 的提纲笔记。
- 如果返回数据明显支撑另一种章节顺序，不要机械照搬参考结构。
- 每个主要章节都尽量遵循“短结论 -> 证据 -> 含义或过渡”的行文方式。
- 不要停留在“罗列总量、排序和占比”。至少要把其中 2-3 个核心章节写成“结构判断/趋势判断 -> 关键数字 -> 原因解释或治理含义”。
- 对行业、属地、主体结构等章节，优先写“头部集中度、梯度差异、重点板块压力、为何会这样”，不要只写“前五名分别是……”。
- 对时间趋势章节，优先识别阶段变化、拐点月份、异常高点/低点及其可能含义；不要把趋势段写成流水账。
- 代表性案例必须服务于前文判断，说明案件机制、风险传导方式或治理薄弱点，而不是孤立地复述案情。
- 如果数据噪声大、不一致或样本稀疏，要把这种限制写进叙事，不要假装没有问题。
- 数据库未连接时，不要伪造总量或统计结果。
- 对于“生成完整报告”这一类请求，默认优先做全区总报告，不要轻易调用 `request_user_input` 去追问目标企业、目标行业或核心关注维度。
- 如果 `pg-report-query` 目前只能返回查询方案，必须明确标注哪些指标仍待执行。
- 如果 `pg-case-search` 目前只能返回检索方案，必须明确标注哪些案例清单仍待数据库执行确认，且本地案例只能用于真实支持当前结论的部分。
- 通常优先选择 1-3 个代表性案例，不要堆砌大量案例。
- 当前默认事实表是 `enterprise_risk_events`。如果只录入了司法案件和行政处罚，不要假装已经覆盖 12345 或综治中心数据。
- 默认不要在正文末尾附“数据库表名 / 关键字段 / 完整列名 / 技术实现说明”。这些内容如果确有必要，应单独作为技术附录，并且只有在用户明确要求时才出现。

在正式写最终报告前，必须先阅读 `references/report-structure.md`。
